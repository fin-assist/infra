# FIN-362: подготовка сквозной API-приёмки

Комплект предназначен для отдельного stage FIN-149 с пятью реальными Go-сервисами,
PostgreSQL 18 и отдельным облачным Object Storage. Только внешние телефонный и LLM-провайдеры
заменяются согласованными fake-phone/fake-llm. Соседи не подменяются in-process фейками.
Базовый runner не является полной приёмкой FIN-362: обязательные оставшиеся проверки перечислены
в [matrix.json](matrix.json). В репозитории нет результата фактической приёмки.

Маршруты и поля проверены по `fin-assist/contracts` main `87e8200` (30.10.2026), `docs/api.md`
1.1–1.6, 2–7 и `openapi/openapi.yaml`. Перед запуском сравнить выбранный набор артефактов с
актуальными контрактами; особенно нужны доказательство согласия/14+ при Start и сохранение
исходной версии при Register. Совпадение SDK само по себе не доказывает совместимость HTTP.

## Базовый прогон

После подготовки и разрешённой выкладки FIN-149 оператор подтверждает изоляцию stage,
`ENV=stage`, `AUTH_MODE=verify`, `PHONE_PROVIDER=fake`, адрес локального fake-llm,
реальные адреса пяти сервисов и PostgreSQL. Нельзя направлять runner на production или реальные
провайдеры. Автоматически доказать fake-провайдеры по публичному API невозможно;
флаг `--confirm-stage-synthetic` фиксирует осознанный выбор оператора, а не такую проверку.
Параметры хоста и секреты в Git не добавляются.

Из корня проверенного checkout infra, на Linux/macOS с Python 3.9+:

```sh
python3 scripts/acceptance.py \
  --base-url https://stage.example.invalid \
  --phone +70000001234 \
  --set /secure/stage-set.json \
  --artifacts /secure/artifacts \
  --report /secure/fin362-smoke-unique.json \
  --client-version android/0.2.14+1 \
  --timeout 300 \
  --confirm-stage-synthetic
```

`X-Client-Version` имеет контрактный формат `<platform>/<semver>+<build>`; передать версию не ниже
настроенного минимума BFF через `--client-version` (по умолчанию `android/0.2.14+1`).
Заменить адрес и выбрать **неиспользованный** номер из service-local синтетического диапазона
`+7000000xxxx`; это не выделенный оператором связи тестовый диапазон, поэтому реальному провайдеру
он не передаётся. Запуск создаёт один аккаунт и три загрузки. Если номер уже зарегистрирован,
runner останавливается до импорта. Данные автоматически не удаляются: после сбоя/успеха оператор
может повторно войти по тому же synthetic phone и выполнить отдельный согласованный cleanup.
Токены остаются только в памяти процесса. Скрипт не выполняет DELETE, SSH, systemctl,
миграции, SQL и команды облака.

Перед первым HTTP-запросом проверяются весь set, manifest/provenance/checksum и единая версия SDK
штатным `stage.verify_set`. Это проверка **предоставленного** набора, не установленных на VPS
бинарей: `deployed_set_verified` в отчёте остаётся `false`. Сопоставить set с immutable release
путями и контрольными суммами реально работающих процессов — отдельное доказательство FIN-149.

Прогон проверяет:

- актуальный personal_data документ; Start с consent/14+; replay того же ключа; verified SSE
  и повторную доставку того же registration_token; Register и его replay;
- refresh с replay в одном 60-секундном окне: локальный абсолютный бюджет пары 45 с
  (не длиннее оставшегося suite deadline), проверка срока до повторной HTTP-попытки;
  после просрочки использованный refresh не повторяется; чтение профиля;
- `basic.ofx`, replay того же multipart/ключа, терминальный progress SSE и reconnect;
  второй импорт того же содержимого с новым ключом (dedup), затем `empty.ofx`;
- ленту, all-time поиск, детали обеих операций, категории и финансовые фильтры `with`/`without`;
- периоды month/quarter/year и блоки аналитики в обоих режимах после bounded ожидания доставки;
- пустую историю/суточный лимит помощника; logout и его повтор.

В basic fixture расход 100 ₽ и доход 1 000 ₽, то есть 10 000/100 000 копеек в обоих режимах.
Импортные суммы и фильтры проверяются относительно этих независимых ожиданий. Наличие блоков
аналитики не доказывает правильность их цифр: сложные суммы/переходы проверяются далее.
При ошибке прогон останавливается, текущий case получает `failed`, последующие не считаются пройденными.
Успешный exit 0 означает только перечисленный smoke; `full_acceptance` всегда `false`.
Готовность аналитики подтверждает только явный `recalculating:false` типа boolean. Строки, числа,
null и отсутствие обязательного флага — отказ; счётчики/суммы oracle требуют JSON integer,
а replay сравнивает также типы (`0` не равен `false`). Это проверки используемых полей, не полный OAS-валидатор.

Операции ограничены idle timeout 15 с и общим SIGALRM 30–600 с (по умолчанию 300 с), включая
slow-drip headers/SSE. JSON/SSE ограничены 4 МиБ, строка SSE — 64 КиБ. HTTP разрешён только
для числового loopback; внешний адрес требует системно проверяемый HTTPS. Proxy, redirect,
cookies, автоматические HTTP-повторы и отключение проверки сертификата отсутствуют.
Отчёт создаётся исключительно новым файлом mode 0600; он не содержит HTTP-тел, телефонов,
user/upload/answer IDs, access/refresh/verification tokens и текста исключений.

## Финансовые fixtures и независимый oracle

Для них нужен **второй новый synthetic account**, отдельно от basic smoke.
[expected.json](expected.json) задаёт последовательность и суммы в копейках:

| Шаг | Ожидание |
|---|---|
| `financial.ofx` | 7 исходных операций, 6 публичных записей: покупка 1 000 ₽, возврат 200 ₽, зарплата 10 000 ₽, человеку −300 ₽/от человека +400 ₽, своя пара −500 ₽/+500 ₽ на двух счетах |
| Режим `with` | Расход 110 000, доход 1 040 000 коп. Своя пара исключена, возврат уменьшил расход |
| Режим `without` | Расход 80 000, доход 1 000 000 коп. Переводы людям также исключены |
| `financial-overlap.ofx` после первой | 2 дубликата + новый расход 50 ₽; 7 публичных записей. Расход 115 000/85 000 коп. (`with`/`without`), доход не изменился |
| `unread.ofx` | Непрочитанная сумма с известными счётом/FITID/датой: `new_count=0`, одна незакрытая строка |
| `unread-fixed.ofx` | Тот же счёт/FITID с исправленной суммой −25 ₽: новая операция, прежняя unread закрыта. Расход 117 500/87 500 коп., доход не изменился |

Результаты этих fixtures пока не проверены реальными сервисами. Python-тесты проверяют их XML,
пересечение FITID, идентичность repair и арифметику oracle, не заменяя production parser/приёмку.
Оператор загружает файлы через `POST /v1/statements`, ждёт `complete`, читает unread по upload ID
и периоду, затем данные через публичные operations/analytics. Не вычислять неизвестные `selection`
самостоятельно: брать `operations_filter`/regular-payment id из ответа сервера.

## Протокол оставшихся доказательств

Каждому элементу matrix соответствует отдельная запись: case, время начала/конца UTC,
infra runner SHA/hash, set пяти сервисов+fake-llm с SHA/run/attempt, hashes fixtures/fake-llm script,
предусловия, выполненные HTTP-операции/операторский шаг, независимое ожидание, фактический результат,
pass/fail/not_run и причина. Сохранять только разрешённые счётчики, суммы синтетического oracle,
статусы/error.code, версии и безопасные корреляции; не публиковать raw HTTP/DB/облачные ответы,
логи с токенами или идентификаторы реального хоста. Приложенные operator reports не должны менять
`full_acceptance` автоматического smoke. Итоговая приёмка — отдельный проверенный отчёт.

1. **Вход и импорт.** Проверить отказы consent/версия/возраст до провайдера, assistant consent
   grant/revoke, overlap/unread repair по таблице выше. Для нового ключа повторный импорт не
   перетирает ручные категории; тот же ключ/тело возвращает прежний upload. Пустая выписка на
   отдельном пустом аккаунте оставляет `has_data:false`, но covered periods доступны по контракту.
2. **Выборки.** Проверить own pair/refund и суммы обоих режимов по oracle; открыть серверный
   `operations_filter` блока аналитики и сопоставить сумму с показанной. Для пагинации нужны
   дополнительные явные периоды нескольких кварталов: читать `next_before` как есть, до конца,
   сверяя уникальность и полный заранее известный набор операций. Basic fixture этого не доказывает.
3. **Правки.** `PATCH /v1/operations/{id}` с `category_id` и исходным `occurred_at`; own pair
   должна вернуть две операции и `replaced_id` пары. Повторный импорт не отменяет ручную правку.
   В `PUT`/`DELETE /v1/analytics/regular-payments/{id}/dismissal` использовать ID реально найденной
   регулярности; проверить повтор/отмену и пересчитанные оба режима. Фиксировать асинхронный
   пересчёт до конечного expected состояния, а не только HTTP 200.
4. **Время/бэкфилл.** Добавить частичные/gap fixtures с явными границами. Проверить stale на
   15-й календарный день после последнего покрытого дня, month/quarter/year и timezone change
   по допустимому `PATCH /v1/profile` сценарию. В согласованное окно выполнить настоящий daily
   job и версионный backfill по действующему runbook BSD: старый снимок виден до целой атомарной
   замены обоих режимов; removed_periods доставлены. Не менять системные часы/production registry
   и не подменять SQL статусами для имитации успеха.
5. **Помощник.** После `PUT /v1/profile/assistant-consent` с текущей version запустить управляемый
   fake-llm сценарий, требующий реальных Overview/Aggregate/Find/GetAnalytics/GetDataVersion.
   Вопрос — `POST /v1/assistant/messages`, SSE — `/v1/assistant/messages/{answer_id}/events`.
   Сопоставить server-built блоки с oracle, replay/done/history/limit; выполнить новую committed
   правку категории, затем history и начальный SSE snapshot должны показать `changed_since`.
   Отдельные пустой и малоданные аккаунты дают реальные NO_DATA/LOCKED, `charged:false`; исчерпание
   суточного лимита не создаёт новый вопрос/вызов модели. Fake доказывает транспорт/сборку данных,
   не качество настоящей модели.
6. **Удаление — отдельное разрешение.** После одобрения оператора удалить только run-owned
   synthetic upload/account публичными DELETE; повтор идемпотентен. Проверить surviving данные,
   новые суммы, encrypted empty fence по утверждённому Object Storage протоколу (не физический DELETE),
   запрет позднего create, доставку purge всем соседям и отказ сессий. Поздний import/recalc/outbox
   не восстанавливает данные. Для storage/purge нужны безопасные операторские доказательства;
   отсутствие записи в публичной истории их не заменяет.
7. **Отказы и изоляция — отдельное окно.** По одобренному operator runbook остановить/восстановить
   конкретный сервис во время импорта, расчёта и доставки; проверить durable повтор без потерь/дублей.
   SSE reconnect должен начинаться с текущего snapshot; обрыв без terminal не считается успехом.
   Два synthetic аккаунта пытаются читать/менять чужие upload/operation/answer: контрактный отказ
   и неизменность владельца. Не использовать реальные данные для этой проверки.

FIN-362 закрывается только после всех обязательных фактических сценариев. FIN-303 остаётся отложенной;
production, платные провайдеры, UI и Android stage-сборка не входят. Само наличие этого runbook,
зелёных Python-тестов или stage set не означает готовность FIN-354.

## Проверка самого инструмента

В Linux CI общий шаг уже использует `timeout 120 python3 -m unittest discover -s scripts -p 'test_*.py' -v`.
Локально без `timeout` можно запускать тот же процесс через
`subprocess.run([...], timeout=120)`; yield/session timeout инструмента недостаточен.
Тесты поднимают локальные HTTP listeners для transport boundary checks. Это тестовые peers самого
runner, которые никогда не выдаются за реальные соседние сервисы в отчёте FIN-362.
